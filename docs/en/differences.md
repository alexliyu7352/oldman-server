# Differences from Sanic

The framework layer comes from Sanic 25.12.1 and keeps most of its interface; for routing, middleware, blueprints, signals and the like, see [the Sanic documentation](https://sanic.dev/). This package no longer aims to match Sanic's public interface. The deliberate differences are listed below, and code written for Sanic, such as oldman, adjusts to them; each change updates the tests in the same commit.

## Interface

- The package is `oldman_server`; there is no `import sanic` alias. Class names drop "Sanic": `Sanic` → `OldmanServer`, `SanicException` → `OldmanServerException`, `DefaultSanic` → `DefaultServer`, `SanicTestClient` → `TestClient` (internal classes drop it too). The configuration environment variable prefix `SANIC_` → `OLDMAN_SERVER_` (for example `OLDMAN_SERVER_NATIVE_SERVER`; not `OLDMAN_`, because oldman's own `OLDMAN_*` variables would be read as settings); logger names `sanic.root` / `error` / `access` / `server` / `websockets` → `oldman_server.*`; process names `Sanic-Main`, `Sanic-Server-*` → `Oldman-Main`, `Oldman-Server-*`. HTML error pages show oldman-server, without Sanic's logo and sanic.dev links; the color `Colors.SANIC` → `Colors.PINK`. Notes in logs and error messages that still point to sanic.dev refer to stock Sanic's documentation (the framework layer comes from it).
- Sanic Extensions are not supported: there is no `app.ext`, `app.extend()` or `AUTO_EXTEND`, and the server does not look for or load sanic-ext at startup (stock Sanic extends the application automatically when sanic-ext is installed). sanic-ext imports the `sanic` package itself and cannot be used with this package's applications.
- setuptools is no longer a runtime dependency (the package does not use it; stock Sanic lists it).
- The test client ships with the package as `oldman_server.testing` (derived from sanic-testing 24.6.0); `app.test_client` needs httpx, and sanic-testing is no longer needed. Unlike sanic-testing: without a configured port every call binds a fresh port the system picks (sanic-testing kept the first call's port, so a call after the server had closed a connection failed with "Address already in use"); a call leaves the app as it was (settings that `debug=True` turns on, such as the access log, are restored, and no 405 handler of its own is registered on the app, so PUT, PATCH and DELETE get the same 405 error page as in production); httpx's `follow_redirects=False` takes effect (`allow_redirects` is its alias); `ReusableClient` takes the same methods and arguments as `app.test_client` and binds a port the system picks; `websocket()` uses websockets' asyncio client, so extra request headers are `additional_headers=` (formerly `extra_headers=`), and the dependency floor is websockets 13.0; in the `(request, response)` a call returns, `response` is never None: a call that gets no response (the server does not start, the connection fails) raises an exception saying why, and the `allow_none=` argument is gone (`request` is None with `gather_request=False` or when the server received no request).
- New `response.abort()`: on a streaming response obtained from `request.respond()`, it closes the connection after the data already sent without completing the response (no final chunk, or fewer bytes than Content-Length), so the client knows the content is incomplete; a later `send()` raises, and the handler is cancelled at its next await (as when the client disconnects). Before any data has been sent it raises `ServerError` (raise an exception or return an error response instead); after the response has ended it does nothing. The asyncio server and the native host behave the same; `request.transport.get_protocol().close()` in oldman's proxy (which has no effect on the native host) can be replaced with it.
- New `@app.rewrite_path`: the registered functions run for every request before routing and all middleware, in the order registered, and return a new path (starting with `/`) or None. From then on the request's `path` and routing use the new path; the query string is kept, and `raw_url` is still what the client sent. An exception they raise goes to the error handler. oldman's `I18nRequest` (which rewrites the private `_parsed_url`) can be replaced with it: a custom request class makes the native host take the full path, while this hook keeps the fast path.
- New setting `UNIX_SOCKET_MODE`: the permission bits of the unix sockets the server binds (`unix=`, `NATIVE_WORKER_LISTEN`), default 0o666 (as in Sanic); it takes `0o660` or an octal string (as an environment variable, `OLDMAN_SERVER_UNIX_SOCKET_MODE=0o660`). A value outside 0–0o777 raises `ValueError` when binding.
- New setting `TRUSTED_PROXIES`: addresses or networks (a list, or a comma-separated string such as `"127.0.0.1, 10.0.0.0/8"`); `"unix"` means unix socket connections (every process that can connect to the socket is trusted; see `UNIX_SOCKET_MODE` for its permissions). When it is set, forwarding headers such as `Forwarded` / `X-Forwarded-*` take effect under `FORWARDED_SECRET`, `REAL_IP_HEADER` and `PROXIES_COUNT` only on connections from these sources; on other connections `remote_addr` is empty, and `client_ip`, `scheme` and `host` come from the actual connection. IPv4-mapped addresses (`::ffff:a.b.c.d`) received by a dual-stack listener are compared against IPv4 networks. A malformed value raises `ValueError` at server startup. Unset, it behaves like stock Sanic: forwarding headers take effect on every connection under those settings.
- New `HTTPMethodView.before_dispatch(request, *args, **kwargs)`: when overridden, it runs before the method handler with the same arguments (it may be a plain function or a coroutine); if it returns a response, that response is sent, and only if it returns None does the handler run; an exception it raises goes to the error handler. Not overridden, it costs nothing. oldman's `HTTPMethodView` no longer needs to copy the whole `dispatch_request`; its sign-in and permission checks can go here.
- New `TooManyRequests` (429, importable from `oldman_server` and `oldman_server.exceptions`): raised when a rate limit refuses a request; like the other 4xx exceptions its traceback is not logged by default. When the wait is known, give it as `headers={"Retry-After": "30"}`.
- HEAD and OPTIONS are answered by the routing layer for every route, without registering routes of their own (settings `HTTP_AUTO_HEAD` and `HTTP_AUTO_OPTIONS`, both on by default): when a route group has GET but no HEAD, a HEAD request is handled by that GET route itself (the same handler, middleware including the blueprint's, decorators and class views; `request.method` stays `"HEAD"`, and no body is sent); when a path has routes but no OPTIONS, an OPTIONS request gets 204 with `Allow` (the path's methods plus the automatic HEAD and OPTIONS, sorted), passing only through the application-level request and response middleware, as a 405 does, and not through the error handler or the exception signals; a 405's `Allow` lists the automatic HEAD and OPTIONS too. Routes registered for HEAD or OPTIONS take precedence; WebSocket routes have neither; a CORS preflight from an allowed origin is answered before routing. Stock Sanic answers HEAD on a GET-only route with 405, and sanic-ext adds automatic HEAD and OPTIONS by registering extra routes.
- New `AsyncTestClient` (`oldman_server.testing`, also as `app.async_test_client`): a test client to `await` inside a running event loop (async tests such as `IsolatedAsyncioTestCase` or pytest-asyncio), where `app.test_client`, which runs its own loop, cannot be called. It serves the app with this package's own server (the native host or the asyncio server, as `NATIVE_SERVER` says) in the current loop and sends real HTTP requests over a local socket with httpx; it has nothing to do with ASGI. Its methods, arguments and return values are those of `app.test_client`. Outside `async with`, every call starts the server, makes one request and stops it; inside, one server serves the whole block and the server listeners run once. In stock Sanic, async tests could only use `app.asgi_client` (ASGI, which this package removed).
- Header values are stripped of whitespace at both ends (RFC 9110 optional whitespace; stock Sanic strips only the start, so `X-A: v␠␠` gives `"v  "` there), on both servers; iterating `request.headers` yields lowercase names (stock Sanic's parser already did, and the native host now does too).
- Status-line reason phrases and error page descriptions follow RFC 9110 (`oldman_server.helpers.STATUS_CODES`, such as 413 Content Too Large, 414 URI Too Long, 416 Range Not Satisfiable and 422 Unprocessable Content, plus 421 and 425), and both servers write them from that one table (the native host takes it at startup); a status not in it gets an empty phrase (stock Sanic writes `UNKNOWN`). Exceptions' default messages change with it (`PayloadTooLarge` says "Content Too Large", for example).
- The listening socket's backlog defaults to 2048 (`oldman_server.constants.DEFAULT_BACKLOG`, as in Gunicorn and Uvicorn), where Sanic's is 100: when a proxy such as nginx opens hundreds of upstream connections at once, `connect()` on a unix socket fails beyond the backlog and nginx answers 502. `run(backlog=...)` still sets it, capped by the kernel at `net.core.somaxconn`.
- JSON uses orjson by default (`json()`, `request.json`, JSON error pages and JSON logs) instead of ujson:
  - Output is compact UTF-8 (non-ASCII characters are no longer escaped as `\uXXXX`); datetime, UUID, dataclass and enum values encode directly; non-str keys are still converted to strings.
  - Integers wider than 64 bits raise `TypeError`; `NaN` and `Infinity` are written as `null` (stock Sanic writes an invalid `NaN`); `Decimal` (DECIMAL columns from database drivers) is encoded as a JSON number, as stock Sanic's ujson does (through `float`, with a double's precision; for the exact decimal value use `json(..., default=str)`); unknown objects no longer have `__json__` or `toDict()` called, and they and strings containing lone surrogates raise `TypeError`. To encode them, use `json(..., default=...)`.
  - `request.json` is parsed with orjson: integers wider than 64 bits become `float` (losing precision), and `NaN` and `Infinity` are rejected (400); for exact big integers use `OldmanServer(loads=json.loads)`.
  - In JSON and text error pages, a context value the encoder does not know is shown as its `str()`, so the error response itself does not turn into a 500.
  - Extra keyword arguments to `json()` go to orjson (`default`, `option`, such as `option=orjson.OPT_SORT_KEYS`); `json_dumps` returns bytes. To use another encoder, `json(..., dumps=...)` or `OldmanServer(dumps=..., loads=...)` still work.

## Removed

- The command line (the `oldman-server` command and `python -m oldman_server`, including the `--simple` static file server): start the application with `app.run()` or a higher-level framework's own command; `AppLoader` still loads the application in multiple processes.
- The static directory listing page (`app.static(..., directory_view=True)` and `DirectoryHandler`'s `directory_view`): a directory answers only with its index file, per `index`.
- The startup banner (the MOTD and the logo; the `motd` and `motd_display` arguments of `run()` / `prepare()`, the settings `MOTD` and `MOTD_DISPLAY`): when the main process starts serving, it logs one INFO line instead (`oldman_server.root`) with the application name, address, mode and number of workers.
- Coffee mode (`app.make_coffee()`, `prepare(coffee=...)`, `--coffee`, an Easter egg in Sanic's logo).
- The REPL (`--repl`, `app.repl_ctx`).
- Running in the background (`--daemon` and the `kill` / `status` / `restart` / `stop` commands): process management is left to systemd or oldman's own service commands.
- The inspector (the `INSPECTOR*` settings, `app.inspector`, the `inspect` command).
- TLS (the `ssl` and `auto_tls` arguments of `run()` / `prepare()` / `create_server()`, `--cert` / `--key` / `--tls` / `--auto-tls`, settings such as `LOCALHOST` and `LOCAL_CERT_CREATOR`, `certloader_class`, `conn_info.ssl` / `cert` / `server_name`) and HTTP/3 (the `version` argument, `--http` / `-1` / `-3`, `request.stream_id`, `Alt-Svc`): a front-end proxy terminates TLS, and `request.scheme` still comes from `Forwarded` / `X-Forwarded-Proto`.
- ASGI: the application is no longer an ASGI callable, and `app.asgi`, `app.asgi_client` and `request.scope` are removed with it; it runs only on this package's own servers.

## Behavior fixes

oldman patched these itself; those patches can be deleted after switching.

- On SIGTERM while workers are starting, the main process ends the service instead of waiting forever for the workers to acknowledge (Sanic 25.12.1 spins; oldman's `_wait_for_ack`).
- On a stop signal while a worker restarts (`app.m.restart()`, auto-reload, scaling, zero-downtime restarts included), the main process finishes the step in hand, then stops every process, including the one the restart just started and the previous one a zero-downtime restart still keeps, and exits; no process is started once the shutdown has begun. Stock Sanic stops only the processes that exist when the signal arrives, so nothing stops the restarted worker and the main process waits for it forever.
- When a worker fails after acknowledging its start but before serving (`after_server_start`, or the native host failing to start), the main process ends the service, instead of taking the message for the name of a process to restart and leaving a main process with no workers (oldman's `_handle_message`). Only failures during startup end the service: an error from a worker that has already served, while it stops (restart, scale-down), is only logged; a restarted worker that fails before acknowledging (auto-reload reading a file with a syntax error, say) logs an error, and the other workers keep serving (as in stock Sanic). When the server fails to start, `app.run()` raises (stock Sanic only logs and returns normally, with exit code 0).
- No error when the multiprocessing start method is already set to the one this package needs (oldman's `prepare_process_context` sets `START_METHOD_SET` directly).
- Server listeners run in pairs: when `before_server_start` fails, `after_server_stop` still runs; when `after_server_start` fails, the server stops as usual and `before_server_stop` and `after_server_stop` run; when `before_server_stop` fails, the cleanup and `after_server_stop` still run; the failure is raised in the end. A `RuntimeError` raised by a listener is no longer taken for the event loop stopping early and swallowed or run again. (The except cleanup in oldman's `_services_*_server_*`.)
- A serving process installs its SIGINT / SIGTERM handling before its startup steps (`before_server_start` included), and handles them at the Python level. A stop signal received during startup cancels the startup instead of waiting for it: the startup listener running (`before_server_start` or `after_server_start`) is cancelled at its next await, the startup steps after it do not run, and the stop listeners paired with what did run still run (`after_server_stop` when `before_server_start` was cancelled; when `after_server_start` was cancelled, the server stops and `before_server_stop` and `after_server_stop` run). One INFO line in `oldman_server.root` (Startup interrupted by a stop signal) records it, and the process exits normally; a worker managed by the main process ends as a stopped worker, not as a failed start, and the main process serves on. A startup that hangs (a database connect, say) no longer holds the stop until the process is killed without any cleanup. Code that does not await cannot be cancelled: the stop takes effect when it returns. In a single-process run a second signal stops it at once (it raises KeyboardInterrupt in the startup listener, which ends even code that does not await), and `after_server_stop` still runs; a worker managed by the main process stops once, on the first signal, and later ones have no effect: Ctrl+C and a systemd stop reach each worker twice (from the terminal or systemd, and from the main process), and escalating is the main process's job: on another signal, or 2 × `GRACEFUL_SHUTDOWN_TIMEOUT` + 5 s after its shutdown began, it kills the processes still running (a worker stuck in startup code that does not await, say). The process holding the workers' shared state ignores SIGINT and SIGTERM and is shut down by the main process when the service ends (on Linux it also ends with the main process); with stock Sanic a systemd stop ends it first, and every shared-state call of the main process and the workers then fails. Stock Sanic uses the event loop's `add_signal_handler`, and uvloop drops signals that arrive while the loop is not running (between the startup steps), so the process cannot be stopped; on the native host, requests were also answered before the handler was registered, and a SIGTERM then killed the process outright without running the shutdown listeners. `loop.add_signal_handler` is no longer called.
- When `app.run()` (and `OldmanServer.serve()`, `serve_single()`, each test-client call) ends, the SIGINT and SIGTERM handling in place before the run is back, the program's own handlers included. Stock Sanic leaves the run's handling installed: in a single process both signals stay ignored (set for the stop phases), with workers they go to a worker manager that no longer runs, so a later SIGTERM to the process does nothing and Ctrl+C has no effect (a test process that ran a server cannot be ended by `timeout`, say).
- Worker processes receive SIGTERM and stop when the main process exits (including by SIGKILL), instead of becoming unmanaged orphans that still hold the port (Linux; oldman's `_process_group` check can stay for its other child processes).
- When the worker manager ends the service (a worker failing to start, another signal during shutdown, and so on), it kills only the worker processes: stock Sanic calls `killpg` on the workers' process group, which the main process shares, so the main process is SIGKILLed too and neither the `main_process_stop` listeners nor the cleanup of sockets and unix socket files run. Now the main process finishes normally and exits with code 1; a worker that leads its own process group is still killed together with that group.
- The `Authorization` scheme is the header's first word, compared case-insensitively, rather than a substring match: `request.token` accepts only `Bearer` / `Token`, and other schemes (such as `Basic`) give None instead of the whole header; a Basic password in `request.credentials` may contain colons, and invalid base64 counts as no credentials (oldman's `bearer_credential`, `basic_credentials`; to accept only Bearer, use `parse_credentials(header, ("Bearer",))` and check the returned scheme). A single token without a scheme is still treated as a token; a scheme name with no credentials (`Authorization: Bearer`) has no token (`token` is None, where stock Sanic gives an empty string); any whitespace between the scheme and the credentials (a tab, say) separates them.
- An exception raised by response middleware goes to the error handler like one raised by the handler, and the error handler's response is sent without passing through response middleware; stock Sanic only logs it and sends the original response (oldman's session `save_session` replaces the response with a 500 itself for this reason; after switching it can simply raise). For a streaming response the exception is raised at `request.respond()`, and if the handler does not catch it, it likewise goes to the error handler; after catching it, the handler can respond with something else (which does not pass through response middleware). If response middleware fails again while an error response is being sent (including when the error handler itself calls `request.respond()`), the failure is only logged and the error response is sent (as in stock Sanic).
- Chunked request bodies are parsed per RFC 9112: a chunk size may contain only hexadecimal digits (stock Sanic also accepts `0x5` and sizes with whitespace), chunk data must be followed by CRLF (stock Sanic does not check those two bytes), and a chunk-size line (extensions included) is at most 64 bytes, with no control characters in the extensions (stock Sanic limits the line's length only while it has not fully arrived and does not look at the extensions); otherwise 400, as on the native host. An HTTP/1.0 request with `Transfer-Encoding` (RFC 9112 6.1) or a request with more than one `Host` (RFC 9112 3.2) gets 400; an HTTP/1.1 request without `Host` is still accepted, as in stock Sanic.
- A response with `content_type=None` sends no `Content-Type`, instead of the literal value `None` (the default in oldman's proxy).
- `file_stream()` with a Range reads only what remains: when the range is larger than `chunk_size` and not a multiple of it, stock Sanic reads and sends too much the last time, sending more bytes than the `Content-Range` declares. Both servers behave the same.
- Routes, static routes, middleware, exception handlers, listeners and signals added to a blueprint after it was registered are applied like those defined before: under every registration's options (the prefix and version given to a direct registration; the prefix, version and `name_prefix` of the groups the blueprint is in), and the blueprint's (and its groups') middleware and exception handlers apply to them. A blueprint registered through several groups has its middleware applied to the routes of every registration. Stock Sanic re-registered the whole blueprint with its own defaults instead: a blueprint registered through a group failed at startup with duplicate route names, and a directly registered one let the added routes skip the blueprint's middleware (such as authentication). Adding anything to a registered blueprint after its application has started raises `OldmanServerException`.
- Error handlers follow one contract whether they are plain functions or coroutines: a returned response is sent; None falls back to the default error page (unless the handler already answered with `request.respond()`); a framework exception raised by the handler gets that exception's default error page; any other exception is logged and answered with a 500 "An error occurred while handling an error". `ErrorHandler.default()` may be a coroutine and is always awaited. Stock Sanic fell back to the default page on None only for plain functions (a coroutine got the "Invalid response type None" error page), gave a framework exception its own page only when a coroutine raised it (a plain function got a 500), and did not await a coroutine `default()` when the handler raised a framework exception.
- In response middleware, a `file_stream()` response's `body` is None (the content is read when it is sent) and its `processed_headers` are the headers it will send; stock Sanic raised `AttributeError` for both.
- The response helpers (`text()`, `html()`, `json()`, `raw()`, `redirect()`, `empty()`, `file()`, `file_stream()`), `ResponseStream` and `request.respond()` take any Mapping as `headers` (read-only ones and multidicts included, multiple values kept) and copy it into the response's own headers, never changing the caller's object. Stock Sanic's `redirect()` wrote `Location` into the dict it was given (a read-only Mapping raised `TypeError`; a dict reused for several calls kept the `Location`), `file()` and `file_stream()` likewise wrote `Last-Modified`, `Cache-Control` and the like into it, and `ResponseStream` used a given `Header` object as is.
- Running an app again in the same process (another `app.run()`, or each call of the test client) sets debug mode and auto-reload from that run's arguments instead of keeping the last run's; a later `prepare()` of the same run, adding another address, can still only turn them on. Stock Sanic stayed in debug mode for every run after the first debug one.
- Listeners, `app.add_task()` callables and main-process events get their arguments by their signature instead of being called once and called again with other arguments on a `TypeError`: a `TypeError` raised in their body propagates and they do not run twice (stock Sanic called them again with `(app, loop)` and logged a misleading "loop argument is deprecated" warning).
- WebSocket messages are received in the order they arrive, and the end of the connection (a normal close or a lost connection) comes after them: `recv()` and `async for` first return every message received before the close, then `recv()` raises `ConnectionClosedOK` (a normal close: `async for` ends, the code after the loop runs and `websocket.handler.after` is dispatched) or `ConnectionClosedError` (a lost connection or a protocol error). A `recv()` that times out or is cancelled (`asyncio.wait_for`) loses no message and can be called again. When the connection ends, a handler that is waiting for a message or has messages left to read learns of it through `recv()`; one that is not reading is cancelled, as a request handler is when its client leaves; a later `send()` on the closed connection (`WebsocketClosed`) counts as the client leaving, without `websocket.handler.exception`. Stock Sanic signals a close by cancelling the waiting `recv()`: `async for` raises `CancelledError`, messages that arrived before the close can be lost, `websocket.handler.after` is not dispatched, and after one `asyncio.wait_for(ws.recv(), t)` timeout every `recv()` raises `ServerError`. Both servers behave the same.
- The `Connection` header is parsed as a list of options, possibly over several fields: only a `close` option ends the connection (for HTTP/1.0, the lack of a `keep-alive` option). Stock Sanic compared the whole value with `keep-alive`, so `Connection: Upgrade`, `keep-alive, Upgrade` (as Firefox sends) and `TE` closed the connection, and only the last field counted. Both servers behave the same.
- `shared_ctx` is set only in `main_process_start`: assigning to it in a worker process (or in a single-process run once it serves) raises `RuntimeError`, pointing to `app.ctx`. Stock Sanic has the lock, but it decided whether the process was a worker before the worker was set up, so it never took effect and an object put there in a worker stayed in that worker without any warning.
- `main_process_stop` runs in the reverse of its registration, like the other stop events (what was set up first is released last); stock Sanic runs it in registration order (the reversed list it prepares is never used).
- The worker manager stops server processes (service stop, restart, scale-down) with SIGTERM, where stock Sanic uses SIGINT: a worker still importing its modules, its signal handling not set up yet, ends quietly instead of raising `KeyboardInterrupt` at the line it was importing and printing a traceback; once set up it handles both signals alike. Processes started by `app.manager.manage()` still get SIGINT (`KeyboardInterrupt`).
- `RESPONSE_TIMEOUT` runs until the response starts (a streaming response's first send) and not after; stock Sanic times the gap between sends, so a stream that sends slowly (such as SSE) is cut off. When the client stops taking the response, a write that waits longer than `KEEP_ALIVE_TIMEOUT` + `GRACEFUL_TCP_CLOSE_TIMEOUT` closes the connection and cancels the handler as the client leaving does; stock Sanic's asyncio server has no such deadline. Both servers behave the same.
- A static file (`app.static`) answers HEAD with the header fields GET sends (`Content-Length`, `Cache-Control` and the rest), without the body; stock Sanic answers it on a branch of its own with `Content-Length: 0` (unless `use_content_range` is set) and no `Cache-Control`.

- Configuration: upper-case class attributes of a `Config` subclass are default settings (the rule `update_config(a class)` reads a class by), seen by `get()`, by iteration and by the native host, and overridden by the environment and later assignments; in stock Sanic they worked only for attribute reads, assignments did not change them and `get()` did not see them (so native host settings given that way were ignored). Settings with a setter (`FALLBACK_ERROR_FORMAT`) given in `Config(defaults=...)` take effect. A context object passed as `OldmanServer(ctx=...)` is used even when empty (an empty dict subclass, say) instead of being replaced by a `SimpleNamespace`. `PROXIES_COUNT` is checked when the server starts (None or a non-negative integer, else `ValueError`), not with an assert per request.

## Under the native host

- `request.headers` is a `NativeHeaders`: `[]`, `get`, `getone`, `getall`, `in` and attribute access (`headers.content_type`) look up the native request directly; iteration, `items()`, `len()`, `==`, `copy()` and modification build a `Header` on first use and work on it from then on, with the same results as `Header`. It is a `multidict.MultiMapping` (and a `Mapping`) but not a `CIMultiDict`: `isinstance(request.headers, CIMultiDict)` is False.
- Empty lines before the request line are skipped per RFC 9112 and count toward the header limit (`REQUEST_MAX_HEADER_SIZE` and the like), with 413 beyond it; stock Sanic answers 400 to any leading empty line.
- `request.head`, `raw_headers` and `request_line` are rebuilt from the parsed request line and fields (one space after the colon, values stripped at both ends, names in the client's case), not the raw bytes the client sent.
- When `file()` (which `app.static` also uses) answers with a file of 128 KiB or more, the content is not read into Python: the handler only opens the file (raising in the handler, as in stock Sanic, if it cannot be opened), and when the response is sent, the native host reads the file and writes it straight to the connection. Response middleware sees `response.body` as None; if middleware sets another body, that body is sent. `Content-Length` is the file's size when opened; if the file shrinks afterwards, the connection is closed after the data already sent. Such a response is not limited by `NATIVE_MAX_RESPONSE_SIZE`. Smaller files, and the asyncio server, still read the file into `response.body`.
- Responses carry at most 128 header fields, about 8 KiB in total; beyond that, the error handler takes over (500). The asyncio server has no such limit (behind nginx, nginx's default `proxy_buffer_size` holds only 4 or 8 KiB of upstream response headers anyway).
- The five connection- and I/O-level signals `http.lifecycle.begin`, `http.lifecycle.read_head`, `http.lifecycle.read_body`, `http.lifecycle.send` and `http.lifecycle.complete` are not dispatched; only the asyncio server dispatches them. The other `http.*` signals are dispatched at the same points.
- `request.protocol` is a stand-in for the native connection: it provides `state`, `version` and `conn_info`, and is not an `HttpProtocol` instance.
- The default native run has no worker manager, so there is no `app.m` (multiplexer). This is the same as stock Sanic with `single_process=True`.
- Native WebSockets do not construct a `WebSocketProtocol`, but are handled by `WebsocketImplProtocol` all the same, and the `WEBSOCKET_*` settings apply.
- With `NATIVE_SHARDS` set, `fast=True` starts CPU count ÷ (1 + `NATIVE_SHARDS`) workers instead of one per CPU, since each such native worker takes a group of CPUs. Unset, it starts one per CPU as stock Sanic does (in same-thread mode).
- `app.create_server()` starts serving once created: `asyncio_server_kwargs` (such as `start_serving=False`) apply only to the asyncio server.
- When the native host starts serving, it sets the garbage collector's first threshold to 10000 (`NATIVE_GC_THRESHOLD`, only while the process still has Python's default; see [Configuration](configuration.md#native-host-settings)), for the whole process; stock Sanic leaves the garbage collector alone.
- Requests cut off at shutdown are not logged separately as `Request: ... stopped. Transport is closed.` (the asyncio server logs them).
- Requests with `Expect: 100-continue`: when the body has not arrived yet, the native host answers `100 Continue` before handing the request to Python (not when the whole body has arrived with the headers, which RFC 9110 allows). Stock Sanic answers it at the first read of the body; non-stream routes read the body before the handler, so there it is likewise immediate, and only when `stream=True` and the handler responds without reading the body does stock Sanic send the 100 together with the response.
- `REQUEST_TIMEOUT` for the headers counts from the request's first byte, where stock Sanic counts from the last data received, so a client sending its headers slowly, one byte at a time, cannot hold a connection indefinitely.
- When a request body exceeds `REQUEST_MAX_SIZE` (a `stream=True` handler still reads all of it), the connection closes after that request's response; stock Sanic keeps it alive once a stream handler has read the body.
- Graceful shutdown, as in stock Sanic, first stops accepting new connections and closes idle ones; busy connections keep being served (pipelined requests already received included), and in-flight requests get `GRACEFUL_SHUTDOWN_TIMEOUT` to finish and have their responses written. The difference: a busy connection is closed after its last response (which carries `Connection: close`), where stock Sanic keeps it alive and cuts it off only when the grace period ends. After the grace period, handlers still running are cancelled, and their requests get no answer at all: the connection is closed (as on the asyncio server and in stock Sanic; a proxy can retry an idempotent request on another worker). They are given at most 1 more second: a handler that ignores the cancellation and keeps running is left behind (with a warning), and the server stops as usual (stock Sanic does not wait for it either when it closes the event loop). The asyncio server stops in the same order on asyncio's built-in event loop from Python 3.12 (Windows, `USE_UVLOOP=False`); there, stock Sanic first waits for every connection to close by itself (idle keep-alive ones included) before starting these steps, so its shutdown can wait forever.
