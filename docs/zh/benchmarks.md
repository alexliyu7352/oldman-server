# 性能对照

oldman-server 与原版 Sanic 25.12.1 在同一台机器、同样 CPU 下的完整对照，以及本项目各阶段的变化。README 的数字取自这里。吞吐（RPS）越高越好，每请求 CPU 与延迟越低越好；比原版差的格子标 **↓**。

## 一览

前六行（配对对照）为 2026-10-27，代码 `956ef97`。wrk 五行为 2026-10-25，代码 `7efd8fe`，两行静态文件是 `378f09e`（大文件改由原生主机直接写入连接）之后重量的；之后没有重量。

| 场景 | 本项目 RPS | 原版 Sanic RPS | 倍数 |
|---|---:|---:|---:|
| 单进程（3 核），小 JSON | 159,028 | 76,469 | 2.07 |
| 单进程（3 核），回显 1 KiB 请求体 | 132,466 | 65,534 | 2.01 |
| 单进程（3 核），handler 等 1 ms 计时器 | 117,421 | 84,784 | 1.39 |
| 4 个 worker（4 核），小 JSON | 251,376 | 100,814 | 2.50 |
| 4 个 worker（4 核），回显 1 KiB 请求体 | 223,347 | 86,306 | 2.59 |
| 4 个 worker（4 核），handler 等 1 ms 计时器 | 186,170 | 104,483 | 1.76 |
| wrk，空文本路由，256 连接 | 214,974 | 129,263 | 1.66 |
| wrk，handler 自己花 25 µs CPU | 89,876 | 69,958 | 1.28 |
| wrk，每个请求一条新连接，256 并发 | 43,877 | 25,040 | 1.75 |
| wrk，静态文件 4 KiB | 23,512 | 11,346 | 2.07 |
| wrk，静态文件 256 KiB | 10,057 | 7,092 | 1.42 |

每请求的服务端 CPU 都低于原版（原版的 0.39–0.78 倍）。

2026-10-26 的 `9b600a7`–`6fcf554`：shard 上每请求更少的内存分配，快速路径的几处精简，原生主机交给 Python 的请求对象从 pybind11 类改为普通的 C 扩展类型；直接挂在原生主机上的普通函数不再经过 Task，同线程模式下由 shard 在连接循环里直接调用并写回（框架的 handler 仍各在一个 Task 里运行）。与 2026-10-25 相比回显提高最多（1.42 → 1.57 倍）。

之后的 `726ee60`–`2eb41f2`：引擎对每个框架请求的记账更少（完整的请求直接建 Task，回答原样排队）；同一个请求目标（路径与查询）的解析结果在请求之间共用，改写路径的请求仍各有自己的一份；常见响应的收尾内联；框架回答的状态与响应头只检查一次。单进程三项为 1.84 / 1.69 / 1.21 倍（`6fcf554` 为 1.60 / 1.57 / 1.14），4 个 worker 为 2.28 / 2.33 / 1.66 倍。

再之后的 `52d7090`–`16fd826`：框架的协程自己结束请求，不再经过引擎的回调；同线程模式下取请求的循环直接为框架的 handler 建 Task；没有响应中间件、也没有 `http.lifecycle.response` 信号的应用，建立 Request（连同设定 `Request._current`）与写回普通响应并结束请求（连同复原 `Request._current`）各在原生主机的一次调用里完成；快速路径的路由查找结果改由路由器自己保存，路由表重建时一起作废。单进程三项为 2.05 / 2.00 / 1.25 倍，4 个 worker 为 2.51 / 2.59 / 1.73 倍。

2026-10-27 的 `b91b272`–`956ef97`：同线程模式下 shard 调用裸函数时不再经过两层 Python 方法，检查、在 context 的副本里运行、记账与拆开回答都在原生的那次调用里完成；连接循环先用一次非阻塞的 send 写出缓冲的响应，写不完的才交给 Asio（只在 epoll：io_uring 的写本来就和环里的其他操作在同一次系统调用里提交，单独 send 反而更贵）；原生主机开始服务时把 Python 垃圾回收的第一代门槛调高到 10000（`NATIVE_GC_THRESHOLD`，见下文[单进程](#单进程3-核)）。单进程三项为 2.07 / 2.01 / 1.39 倍，等计时器的 p99 从 8.97 降到 5.31 ms；服务端 2 个 CPU 满载时裸函数每请求 10.06 → 9.05 µs。

## 环境

- 机器：AMD Ryzen 7 3800X（8 核 16 线程），32 GB 内存，Ubuntu 20.04.6，Linux 5.15。
- CPython 3.14.7（普通 GIL 构建），两边都运行在 uvloop 0.22.1 上（对照驱动逐个窗口检查）。
- 本项目 0.1.0，原生主机用默认的 epoll，另测了 io_uring。原版 Sanic 25.12.1（`upstream/sanic.json` 的归档，对照前逐个文件核对）。
- `json()` 用各自的默认：本项目 orjson 3.13.0，原版 ujson 6.0.0。
- 服务端、客户端、驱动各自绑定不同的物理核。测量时机器空闲：配对对照（2026-10-27）每个窗口服务端核上其他进程的占用都是 0，wrk（2026-10-25）最多 0.13 核。

## 方法

**配对对照**（`probes/sanic_comparison/run.py --python-only`）：

- 客户端是本仓库的 `build/http_load`（基于 Asio）：持久连接、闭环，逐个校验每个响应（状态、正文、进程号）。
- 每种业务先跑 2 个 A/A 窗，再让本项目与原版交替跑 4 对；每窗 2 秒预热、5 秒测量。倍数是 4 对吞吐比的几何平均。
- 业务：
  - 小 JSON：返回 `{"message":"Hello, World!"}`。
  - 回显：POST 1 KiB 请求体，响应带回它。
  - 等计时器：handler `await asyncio.sleep(0.001)` 后返回小 JSON，代表等数据库或其他服务的 I/O 型业务，不含客户端库自身的开销（那部分对任何框架都一样）。
- 单进程：服务端 3 核。本项目 1 个进程（1 个 Python 线程 + 2 个 shard 线程），原版 3 个 worker。客户端 3 核，128 条连接（等计时器 512 条）。
- 多 worker：服务端 4 核。本项目 4 个 worker（默认的同线程布局，每个 worker 一个 CPU），原版 4 个 worker。客户端 3 核，256 条连接（等计时器 1024 条）。
- 每请求 CPU：服务端进程树用掉的 CPU 时间除以请求数。延迟：客户端记录的每个请求的 p50 / p99；闭环测量下主要是排队（连接数 ÷ 吞吐）。

**wrk 参照**（`probes/wrk_comparison/run.py`）：

- 路由与 [web-frameworks-benchmark](https://web-frameworks-benchmark.netlify.app/) 相同（`/` 空文本），另加 handler 自己花 25 µs CPU 的 `/work` 和 `app.static` 的两个文件。
- 服务端 4 核，wrk 在另外 3 核。wrk 不校验内容，只统计非 2xx（全部为 0）。
- 每格 2 轮、交替顺序，每轮 3 秒预热、10 秒测量，取平均。
- 服务：
  - 本项目 4 个 worker（默认的同线程布局）；
  - 本项目 2 个 worker × (1 个 Python 线程 + 1 个 shard)；
  - 裸函数：不经框架、直接挂在原生主机上的一个 Python 函数，即原生主机自己的上限，两种布局都测；
  - 原版 4 个 worker。

每一对的吞吐都领先原版。等计时器的 p99 在每一对都低于原版（本项目四次为 5.2–5.4 ms，原版 8.0–9.9 ms，两种后端相同）。`16fd826` 时这一格在各对之间起伏大，epoll 时还高于原版（8.97 对 8.32 ms，本项目四次为 7.9–11.0 ms），原因是 Python 的垃圾回收：512 个在途请求的对象在每次年轻代回收时都还活着，默认门槛（2000）下约每 7 ms 回收一次并把它们升代，于是约每 0.75 秒触发一次完整回收，每次 7–8 ms、什么都收不回，期间所有在途请求一起等。现在原生主机开始服务时把第一代门槛调高到 10000（`NATIVE_GC_THRESHOLD`，见[配置](configuration.md#原生主机的设置)），完整回收不再出现，主线程每请求的时间也少了约 8%。单进程的吞吐由 Python 主线程决定（它总是接近满一核），约为 1e6 ÷ 主线程每请求的 µs。

### handler 自己花 25 µs CPU（`/work`，256 连接）

| 服务 | RPS | 每请求 CPU µs | p99 ms |
|---|---:|---:|---:|
| 本项目，4 个 worker（默认） | 89,876 | 44.1 | 3.59 |

业务本身越重，框架省下的那部分占比越小；2 × (1 + 1) 只有两个核跑 Python，在这里低于原版，所以多 worker 的默认是同线程布局。

| 服务 | 32 并发 | 256 并发 | 每请求 CPU µs（256） | p99 ms（256） |

### 静态文件（`app.static`）

| 服务 | 4 KiB，256 连接 | 每请求 CPU µs | 256 KiB，64 连接 | 每请求 CPU µs |
|---|---:|---:|---:|---:|
| 本项目，4 个 worker（默认） | 23,512 | 169.0 | 10,057 | 397.0 |
| 本项目，4 个 worker，io_uring | 23,489 | 168.9 | 9,982 | 399.8 |
| 本项目，2 × (1 + 1) | 17,378 | 160.3 | 8,970 | 382.9 |
| 原版 Sanic，4 个 worker | 11,346 | 347.4 | 7,092 | 553.0 |

`378f09e` 之前，`file()`（`app.static` 也用它）把整个文件读成 Python 的 bytes，原生主机再复制一份写出，文件内容在内存里多复制了几次，还要为每个响应重新分配大块内存（剖析里缺页与内存分配约占三成 CPU）。256 KiB 的文件在默认布局下因此比原版慢 14%（6,092 对 7,057，每请求 CPU 655.5 对 555.9 µs）。现在 128 KiB 以上的文件不经 Python，由原生主机的文件线程读出、shard 直接写入连接（与 `file_stream()` 相同），是原版的 1.42 倍。更小的文件读进响应反而更省（逐个大小比较，两种做法大约在 100 KiB 打平），所以照旧；4 KiB 一列与改动前相同（之前 23,686 对 11,520）。

## 与其他 Python 框架（wrk）

2026-10-27，本项目代码为 `956ef97`。[web-frameworks-benchmark](https://web-frameworks-benchmark.netlify.app/) 的 Python 应用（the-benchmarker/web-frameworks 的提交 `eb2f909`；网站同样用 CPython 3.14）照它们自己的写法与配置运行，与本项目同机、同样的服务端 CPU：

- 三条路由与网站相同：`GET /` 空响应、`GET /user/0` 回 `0`、`POST /user` 空响应。每个服务启动后先核对三条路由的响应，本项目另查运行在 uvloop 上。
- 服务端 2 个 CPU 与 4 个 CPU 各量一组。每个服务的 worker 或进程数等于服务端 CPU 数（按 CPU 数决定的设 `PYTHON_CPU_COUNT`）；本项目为同线程 worker，每个 CPU 一个。
- wrk 3 个线程在另外 3 个 CPU；64 与 256 连接，每格 2 轮、交替顺序，每轮 3 秒预热、10 秒测量。全部 2xx，没有 socket 错误；服务端 CPU 上其他程序的占用不超过 0.10 核。
- 版本：fastpysgi 0.6、weft-server 0.1.1、wred 0.13、oxapy 0.11.5、Robyn 0.88.0、Emmett 2.8.2（Granian 2.8.5）、Sanic 25.12.1、BlackSheep 2.6.4、Starlette 1.10.0、Litestar 2.25.0、FastAPI 0.162.0、lihil 0.2.41、asgineer 0.9.5；ASGI 应用由 uvicorn 0.54.0 服务；用 uvloop 的都是 0.22.1。
- 网站上的 peregrine（只有 manylinux_2_35 的 wheel）与 socketify（没有 CPython 3.14 的 wheel）在 Ubuntu 20.04 上装不上，没有测。

oxapy 没有用满服务端的 4 个 CPU（3.1–3.8 核），所以每请求 CPU 较低，RPS 却低于本项目与 wred。

### 名次

- 不经框架的函数：服务端满载（2 个 CPU）时本项目排第一，9.05 µs，weft-wsgi 10.05、fastpysgi 10.13，少约 10%（`16fd826` 时为 10.06 对 10.02，并列）。省下的约 1 µs 来自同线程模式下 shard 直接完成裸函数的调用与记账，以及连接循环先用一次 send 写出响应。4 个 CPU 时三者都受 wrk 所限（RPS 约 31–32 万），本项目的每请求 CPU 仍最低。
- 框架：服务端满载（2 个 CPU）时本项目排第一，13.7 µs，wred 14.3、oxapy 15.8。对 wred 领先约 4%，主要在 `GET /user/0`（13.9 对 15.0 µs），`GET /` 与 `POST /user` 少约 0.3 µs。4 个 CPU 时按每请求 CPU 与 oxapy 并列第一（14.54 对 14.51 µs，oxapy 没有用满 4 个 CPU），wred 15.14，两种连接数的 RPS 本项目都最高。oxapy 的路由与请求处理在 Rust 里，Python 端只有同步的 handler；wred 是约 120 行的 ASGI 微框架（跑在 weft 上），按路径查字典找到 handler，handler 直接返回（正文, 响应头, 状态），没有中间件、信号、异常处理与请求生命周期；weft 自己驱动 ASGI 的协程，不为每个请求建 asyncio Task。本项目保留了这些框架功能和每请求一个 Task（contextvars、取消、超时都靠它），满载时每请求 CPU 是原版 Sanic（29.4 µs）的 0.47 倍。
- `6fcf554` 时用 perf 看本项目的框架路由（2 个 CPU 满载）：内核的网络收发约占 39%，Python 约 35%（分散在框架的快速路径、每请求 Task 的建立与调度、请求与响应对象上，没有单个热点），原生主机约 14%，libc 约 6%。内核那部分每请求约 6 µs，对各家都差不多。

## 挂上 oldman 的五个扩展

本包原先随附 sanic-ext 25.12.0 的 fork（`oldman_server.ext`），这一节对照过两边挂上 oldman 那五个扩展后的成本（最后一次 `956ef97`，4 个 CPU：本项目 21.2 µs，原版 + sanic-ext 45.6 µs）。之后扩展从本包移除，模板、CORS 这类配套改由 oldman 自己提供，这组对照不再维护；以前的表格见本仓库在 `8018234` 的 `BENCHMARKS.md`。

## 没有覆盖的

- nginx 等反向代理在前时：代理自身的成本对两边相同；多 worker 在 nginx 之后的请求分配见[部署](deployment.md#放在-nginx-之后)。
- 超过 4 核：这台 8 核的机器上服务端最多分到 4 核（另外 3 核给客户端、1 核给对照驱动），更多核的服务端在这里测不了。客户端 3 核按每请求约 10 µs 的客户端 CPU 估计在 30 万 RPS 左右饱和。
- TLS、HTTP/2、HTTP/3：本项目只服务明文 HTTP/1.1，TLS 由前端代理终止。
- 客户端库（Redis、MySQL、HTTP 客户端）的成本：对任何框架都相同，没有计入。

## 复现

先按[开发](development.md#开发环境)准备开发环境（`bash scripts/bootstrap.sh`，再 `source scripts/env.sh`），把 `upstream/sanic.json` 的归档解压到 `build/sanic-upstream/`。每组之前最好等机器安静（桌面程序会占核）：

```sh
python probes/sanic_comparison/run.py --python-only --out build/gate-single                              # 单进程 3 核
python probes/sanic_comparison/run.py --python-only --server-cores 4 --workers 4 --out build/gate-workers # 4 个 worker
OLDMAN_SERVER_NATIVE_REACTOR_BACKEND=io_uring python probes/sanic_comparison/run.py --python-only --out build/gate-single-io_uring
python probes/wrk_comparison/run.py --out build/wrk-root --services candidate,candidate-shards,bare,bare-shards,stock,candidate-io_uring
python probes/wrk_comparison/run.py --out build/wrk-work --path /work --connections 256 --services candidate,candidate-shards,stock
python probes/wrk_comparison/run.py --out build/wrk-close --close --connections 32,256 --services candidate,candidate-shards,bare,stock,candidate-io_uring
python probes/wrk_comparison/run.py --out build/wrk-small --path /static/small.bin --connections 256 --services candidate,candidate-shards,stock,candidate-io_uring
python probes/wrk_comparison/run.py --out build/wrk-large --path /static/large.bin --connections 64 --services candidate,candidate-shards,stock,candidate-io_uring
bash probes/framework_comparison/setup.sh                                   # web-frameworks-benchmark 的应用与各自的环境（build/framework-comparison）
python probes/framework_comparison/drive.py build/frameworks-2cpu --server-cpus 2   # 全部服务，服务端 2 个 CPU
python probes/framework_comparison/drive.py build/frameworks-4cpu                   # 服务端 4 个 CPU
```

配对对照的每个窗口都写入 `row.json`（吞吐、延迟、每请求 CPU、服务端核上其他进程的占用），wrk 的每个窗口写入 `rows.jsonl`。
